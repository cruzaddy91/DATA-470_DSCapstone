Backorder risk, model evidence, and plain-English talk tracks

Addy Cruz | DATA-470 Capstone | Westminster University

30-Second Story opening

I built an early warning system that predicts which SAP order lines are most likely to become backorders, using only information available when the order is placed.

Problem: backorders delay customers; overstock ties up working capital. The goal is not to magically fix inventory, but to help planners know which orders deserve attention first.

Project factPlain-English meaning
31,177 order linesThe model learned from a meaningful order history.
3.38% positive rateBackorders are rare, so accuracy alone is not enough.
6,521 temporal test rowsFinal check used later orders the model had not trained on.
58 test positivesSmall positive count makes the evaluation strict and sometimes unstable.

Flow and Leakage Guardrails plain english

StepWhat happenedWhy it matters
1Raw SAP CSVs became cleaned sales, delivery, billing, inventory, purchasing, and master-data tables.Creates a repeatable pipeline instead of one-off spreadsheet work.
2Built the v2 order-time modeling table.Only uses facts that would be known when the order is placed.
3Trained on older orders and tested on newer orders.Matches the real question: can past history predict future backorders?
4Removed future-looking columns like outstanding quantity, delivery status, billing status, and backorder amount.Prevents the model from getting answers it would not have in real life.
Randomly mixing old and new orders is like studying with some of the test answers accidentally included. It can make the model look smarter than it really is.

Edge Cases and Weak Spots gotchas

IssueSimple explanationAnalogy
Rare positivesBackorders are uncommon, so the model must be judged on how well it catches rare events.A fire alarm is judged on rare fires, not ordinary quiet days.
Label maturitySome newer orders may not have had enough time to reveal the true outcome.Grading a test before every student has turned it in.
Recent holdout collapseA very small number of recent backorders can make the score swing dramatically.Judging a fire alarm during a week with almost no fires.
Distribution driftOlder business patterns may not match newer order behavior.Practicing against last year's team, then facing this year's team.
Rolling features hurtSome added history features inherited incomplete labels and changing patterns.Building a weather forecast from a thermometer that stopped reporting reliably.

Likely Questions answers

QuestionAnswer you can say out loud
Why not use accuracy?Because backorders are rare. A model could say "no backorder" almost every time and look accurate while missing the useful cases.
Why temporal split?In real life, we use past orders to predict future orders. Testing older-to-newer is more honest than mixing time periods.
Why LR if stack was selected?The stack won the formal selection process, but logistic regression was simpler and stronger on the final future-facing test.
Why did feature engineering hurt?The added features depended on history that was incomplete or changing. More features are not always better if the source signal is shaky.
Is it production-ready?The model clears basic performance checks, but I would wait for better label maturity before deploying it.

Future Plans roadmap

Short version: the next lift probably comes from better business signals, not just fancier algorithms.

  • Add better order-time signals: available-to-promise status, inventory buffer, supplier/material lead time, plant capacity, purchase order timing, and customer/material history.
  • Score at more than one moment: keep the order-time model, then add a second checkpoint closer to ship date when more inventory and confirmation data is available.
  • Use fresher training windows: train on recent years instead of decades if business patterns have changed.
  • Split the problem into smaller groups: build separate models by plant, material family, or customer segment when there are enough backorder examples.
  • Change the model structure if needed: move from one universal classifier to a staged system: first flag possible risk, then estimate urgency, then recommend planner action.
  • Improve labels first: wait for outcomes to mature before judging the newest orders, so the model learns from a complete answer key.

Hard Question Anchor fallback

The capstone value is that it separates model quality from data readiness. The model is promising, but the deployment decision depends on whether the newest outcomes are complete enough to trust.
