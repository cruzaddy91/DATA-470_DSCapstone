Abstract

Supply and fulfillment teams lose time and margin when order lines backorder. This capstone builds a binary risk model for SAP-style order lines using only information available at order time (so the label is not “easy mode” with downstream inventory snapshots baked into the features). The work trains and compares baselines and ensembles, picks a primary model from inner temporal validation on the training time range, and then reports an honest temporal holdout on later orders. The current champion in the repository is an out-of-fold calibrated stacking ensemble; on outer holdout it shows strong ranking ability (ROC-AUC about 0.9) but, under a simple precision/recall deployment gate, it does not clear a recall floor, so the project reports a no-go for deployment as stated, and treats that outcome as part of the result, not something to hide.

A secondary track estimates shortfall magnitude (regression) after the classification story; the main capstone result is the classifier and its time-safe evaluation. [Draft: tighten and shorten to fit final page cap.]

Introduction

[Rough draft] Operations and sales organizations running on SAP (or similar ERP) process huge volumes of order lines. Some lines stall into backorder, which erodes service level, revenue, and planner attention. A defensible data science project must predict risk in a way leadership can trust: in particular, features that only appear after the order (for example, live outstanding quantity and saleable stock snapshots right before shipment) can make a model look good while leaking information.

  • Framing: this repository standardizes a v2 order-time modeling table: one row per (client, sales document, item) grain, target target_backorder_risk for backorder vs not.
  • Evaluation: a temporal split. Train on older order dates, test on later order dates, to approximate future generalization. Inner temporal splits on the training portion support model and threshold choice; the outer temporal holdout is the headline forward-time check, not a place to cherry-pick architecture.
  • Scope honesty: older “snapshot” or alternative experiments exist in the repo, but the official public story is v2 only (see docs/md/v2_model_truth.md).

Methods

Data and grain. The official modeling set contains 31,177 rows at positive rate ≈ 3.38% for the binary target, per models/classification_metrics_v2_ordertime.json. Numeric features at order time include, among others, cumulative order and confirmed quantities, net value, requested lead time, and simple calendar features (month, weekday, quarter). Categoricals include client, item category, sales org, division, plant, country; additional missingness indicators are engineered. A long list of excluded leaky columns is stored in the same JSON (for example, outstanding quantity, saleable inventory, and status fields that are downstream of the order event).

Model zoo. The comparison includes at minimum logistic regression, gradient-boosted trees, and a calibrated stacking ensemble of multiple base learners. Poster-style headlines in internal docs are LR, XGBoost, and the stack; LightGBM and CatBoost also appear as stack components. The champion is oof_calibrated_stack from inner temporal validation on temporal-train rows only (not from peeking at the final holdout).

Metrics. Standard classification metrics: precision, recall, F1, ROC-AUC, and PR-AUC. PR-AUC is especially relevant because the positive class is rare. Thresholds are subject to a calibration and business-style deployment gate (see results).

Protocol. [Draft] Full split definitions, minimum-positive rules for inner test windows, and the rule “do not select the final model from a random ad hoc split on the holdout set” are documented in docs/md/modeling_experiment_protocol.md. Pull section numbers into final prose. Implementation entry points include python scripts/run_modeling.py and the src/models/v2_ordertime/ package.

Notation

[Rough draft. Refine in final pass.]

Target. Let the label y be a Bernoulli random variable in {0, 1} at the order-line grain: y = 1 for backorder risk (positive) and y = 0 for not, under the v2 table definition. A fitted model reports a class-1 score or probability; we write for example P(y = 1 | x) or ŷ for a calibrated or thresholded risk estimate, where x is the order-time feature vector. Subscripts run over rows in the design matrix when a summation is needed: i = 1, …, N.

Temporal holdout. A fixed calendar cutoff, tcut = 2021-07-22, in the current artifact split (see models/classification_metrics_v2_ordertime.json key temporal_holdout.split_date). Training rows have order time strictly before tcut; test rows are on or after, subject to the protocol’s time-range and support rules. “Inner” temporal windows are nested splits on the pre-cutoff data only, used to choose models and calibrate the decision rule before scoring the final holdout.

Results

Champion (selection rule): oof_calibrated_stack - selected from inner temporal validation on temporal-train rows only, per protocol §9 documented in docs/md/modeling_experiment_protocol.md. The stack composes four base learners spanning four model families (linear, boosted tree, bagged tree, instance-based): logistic regression, LightGBM, RandomForest, and k-nearest neighbors. The meta-learner is a class-weighted logistic regression fit on out-of-fold base probabilities computed via TimeSeriesSplit.

Deployable best (single model): logistic_regression - outperforms the stack on outer-temporal F1 and PR-AUC. The choice to highlight LR for deployment, while reporting the stack as the rule-selected champion, is itself a finding (see Discussion).

Outer temporal holdout

Test set: 6,521 rows, 58 positives (0.89% base rate). A random classifier would achieve PR-AUC equal to the base rate (0.009); every model below produces a 20×–40× lift over random in PR-AUC and a strong-discrimination ROC-AUC (≥ 0.91 for the deployable candidates).

The headline reading: at LR’s F1-max threshold, of every 100 actual backorders the model catches 59, and of every 100 orders the model flags 45 are true backorders - on a population whose natural backorder rate is roughly 1 in 113. That represents approximately a 40× lift in PR-AUC over random classification and a ~50× precision enrichment at the deploy threshold.

Methodological contributions surfaced during evaluation

Three correctness defects in the original stack pipeline were identified and remediated. Their measured effects on outer-temporal performance are part of the results, not appendix material:

  1. Threshold-calibration leakage (fixed). The stack’s decision threshold was being chosen against y_test rather than train-only out-of-fold probabilities. Repointing the threshold search to OOF-meta probabilities revealed an honest baseline (stack F1 dropped from a flattered 0.313 to 0.190 before re-tuning) and made all subsequent improvements measurable on a level surface.
  2. OOF random-fold leakage (fixed). The stack’s out-of-fold probability matrix was being constructed via StratifiedKFold(shuffle=True) on temporally-structured data - future rows leaked into earlier-fold training, making the meta-learner calibrate against impossible signal. Replacing it with TimeSeriesSplit lifted the stack’s outer-temporal PR-AUC from 0.244 to 0.326 (a 34% relative improvement attributable purely to validation correctness).
  3. SMOTE asymmetry (fixed). The OOF fold fits applied SMOTE while the final full refit did not. The meta-LR therefore learned a probability mapping that the test-time stack could not reproduce. SMOTE was removed from both sides; class imbalance is now handled solely at base-learner level via class_weight.

Negative results from adversarial experiments

Two attempted lifts were tested and reported even though neither improved performance. Both findings are informative.

  • Temporal-safe rolling features (negative). Per-cohort rolling rates and volumes (plant_backorder_rate_90d, material_order_volume_30d, etc.) were built with strict closed='left' windowing to prevent same-day leakage. Despite correct temporal hygiene, the features hurt stack performance (F1 0.420 → 0.275). Root cause: the most recent 180 days of training data have only 36% mature labels, so the rolling backorder-rate features inherit systematic under-reporting. Tree-based base learners latched onto the bias more than logistic regression. Even target-independent rolling features (volumes, confirmation rates only) failed to lift because of multi-decade train-vs-test distributional drift in volume patterns.
  • Two-stage cascade (no lift). Four cascade configurations were tested post-hoc on existing predicted probabilities. The strongest configuration matched single-model LR’s F1 (0.517) but did not exceed it. Cascading does not create separating signal where none exists in the probability tail; the dataset’s feature ceiling, not the modeling layer, is the binding constraint.

Deployment readiness gate

The deployment readiness check uses three floors evaluated against the rule-selected champion:

  • Precision floor 0.15: stack precision 0.410 - passes.
  • Recall floor 0.35: stack recall 0.431 - passes.
  • Label maturity floor: last-180-days label coverage 36% (minimum 50%); observed positives 32 (minimum 40) - fails.

The model itself clears both performance gates. The overall gate_pass = false status is driven entirely by the label maturity gate, which is a dataset-side condition (recent orders have not had time to materialize as backorders or as confirmed deliveries) and not a model-side defect. This distinction is central to the Discussion that follows.
