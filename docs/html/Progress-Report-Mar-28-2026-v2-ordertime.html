Data Capstone - SAP Backorder Prediction | Order-Time Leakage Mitigation v2

Purpose: Document the March 28 order-time modeling reset, the exact mitigation changes shipped to the repo, and whether those changes reduced validation inflation.

Scope: Raw-to-clean target prep, order-time feature contract, split strategy, notebook governance, new v2 artifacts, and old-vs-new metric comparison.

Status: New order-time dataset contract is live. Notebook training has been retired. v2 artifacts were rebuilt and evaluated on March 28, 2026 using a clean local Python environment.

Why We Intervened

The previous workflow mixed snapshot-style fulfillment state with trainable features, allowed notebook-owned artifact writes, and reported strong grouped metrics even though the temporal holdout collapsed. That pattern pointed to leakage and split inflation rather than true forward generalization.

Observed failure mode: The legacy path could score very high on grouped/random-style validation while still producing a temporal holdout F1 of 0.0000.
Key implication: The goal of this intervention was not to maximize F1 immediately. The first goal was to force the validation process to become honest.

What Changed In Code

Area v2 Change Effect On Overfitting Risk
Dataset contract New trainable table master_order_fulfillment_modeling_v2_ordertime.csv built from order-time fields only. Separates trainable order-time features from legacy snapshot target tables.
Forbidden columns Excluded delivery, billing, inventory, outstanding, backorder, aging, and status fields from v2 modeling input. Removes direct target builders and post-outcome state proxies.
Null policy Kept nulls through dataset assembly and added explicit missingness indicators inside the production prep path. Stops silent fillna(0) from turning missing fulfillment data into a target proxy.
Grain integrity Validated one row per client_id + sales_document_number + item_number before and after the v2 merge. Prevents row expansion and hidden one-to-many leakage.
Split policy Production evaluation now uses grouped holdout plus a calendar-based temporal holdout that expands until the test window has enough positives, with temporal-first model selection. Prevents random row split and prevents meaningless last-20%-of-rows temporal slices.
Notebook governance notebooks/02_modeling.ipynb and notebooks/03_conclusion.ipynb are now read-only viewers of production outputs. Stops notebooks from overwriting model artifacts with leaky training logic.
Magnitude modeling Backorder-units regression was deferred from the official path. Removes a second task that was tied to the same snapshot-style target construction.

Conclusion

The order-time v2 changes did what they were supposed to do first: they reduced the inflated grouped validation results, removed the missing-delivery target artifact, and made the production path much harder to leak. That is a real improvement. The remaining problem is no longer mostly notebook leakage or fulfillment-field contamination. It is that many late-period rows are still unresolved, and the observed positive class remains sparse even after filtering to cleaner labels.

Practical reading: v2 now gives a cleaner and more trustworthy answer than the legacy workflow, but it does not magically create a dense positive class. The next iteration should focus on improving outcome coverage, thresholding under sparse positives, and deciding whether the business wants a longer prediction window or a different positive-event definition.
